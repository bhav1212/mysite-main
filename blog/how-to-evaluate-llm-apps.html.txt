<p>A fluent answer is easy to demonstrate. A dependable application is harder to demonstrate because the unit of success is not a sentence: it is a user completing a task under real constraints. An answer can be well written, grounded in a document, and still be useless if it arrives too late or answers the wrong question.</p>
<p>I would start an evaluation plan with a short product contract: who the application serves, what it is allowed to do, what evidence it needs, and what happens when it cannot finish. The evaluation should test that contract, not reward the model for sounding confident.</p>
<h2 id="section-1">Define success before collecting scores</h2>
<p>Consider a hypothetical assistant that answers employee policy questions. Success includes selecting the policy that applies to the employee, using the effective version, citing the relevant passage, and declining requests outside its permissions. Text similarity to a reference answer captures only a small part of that job.</p>
<p>Separate checks into three groups: task outcome, system behavior, and operational cost. Outcome checks ask whether the response is correct and useful. Behavior checks cover authorization, tool use, and abstention. Operational checks cover latency, retries, and cost per completed task. Do not combine these into one number before looking at the individual failures.</p>
<h2 id="section-2">Keep development and holdout cases separate</h2>
<p>Use development cases while changing prompts and retrieval. Reserve a separate holdout for release decisions, and track how often it has been inspected. Repeatedly tuning against a supposedly frozen test set makes it another development set.</p>
<p>Include representative requests, known incidents, ambiguous inputs, and cases the product should not answer. Where production examples are used, obtain the appropriate permission and remove unnecessary personal or confidential content. Synthetic cases are useful for coverage, but their realism needs checking against actual tasks.</p>
<h2 id="section-3">Use the cheapest trustworthy check</h2>
<p>Validate schemas, required fields, citation destinations, and forbidden actions in code. Use a model judge only for criteria that need interpretation, such as whether a summary preserves an important qualification. Give the judge a specific rubric and test it against independently reviewed examples.</p>
<p>There is no universal number of human spot checks or judge-agreement percentage that makes an evaluation reliable. Review enough examples to expose consequential disagreements, and examine those disagreements by failure type. A judge that consistently misses one serious error can look reassuring in aggregate.</p>
<h2 id="section-4">Make uncertainty visible in the report</h2>
<p>Report denominators alongside rates. A perfect score on three examples is not equivalent to a perfect score on three hundred. Break down results by meaningful task, language, and document categories, while flagging slices too small to support a strong conclusion.</p>
<p>For failures with different consequences, define weights with product and domain owners rather than choosing an impressive-looking multiplier. Keep the unweighted counts visible. A weighted average should not conceal an unauthorized action or another release-blocking event.</p>
<h2 id="section-5">Turn the evaluation into a release decision</h2>
<ul>
<li>Compare the candidate with the current release on the same versioned cases.</li>
<li>Show changed examples, not just the difference between two averages.</li>
<li>Run repeat trials where nondeterminism could change the conclusion.</li>
<li>Define acceptable regressions and non-negotiable failures before seeing the result.</li>
<li>Connect offline checks to a limited rollout, monitoring, and a rollback owner.</li>
</ul>
<p>The useful deliverable is a defensible decision: ship, investigate, or stop. For the next step, see <a href="https://blog.bhaveshjain.com/prompt-changes-production.html">how to release prompt changes</a> and <a href="https://blog.bhaveshjain.com/cost-of-average-accuracy.html">why averages need context</a>.</p>
