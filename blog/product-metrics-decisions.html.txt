<p>A metric becomes useful when a team knows what it would do differently if the number changed. Without that connection, a dashboard can become a monthly ritual: the line moved, somebody supplied a story, and the roadmap stayed the same.</p>
<p>I would begin with the product's intended outcome and work backward to the evidence needed for a decision. The result is usually a smaller, more interpretable set of measures than a collection of every event the application can emit.</p>
<h2 id="section-1">Separate activity from completion</h2>
<p>Imagine a hypothetical self-service export feature. Export-button clicks describe activity. A usable file delivered to the right user describes a service outcome. A successful downstream analysis may be the broader user outcome, though it is harder for the product to observe directly.</p>
<p>Name those boundaries rather than pretending the easiest event is the final goal. A rise in clicks can mean growing use, repeated failures, or a confusing interface. The same line can support incompatible stories unless the surrounding behavior is measured.</p>
<h2 id="section-2">Build a small metric hierarchy</h2>
<p>Use an outcome measure to describe whether the task succeeds. Use diagnostic measures to locate friction, such as invalid requests, queue time, or failed downloads. Add guardrails for consequences that should not deteriorate, such as incorrect data exposure or support burden.</p>
<p>For the export example, the core measure might be the fraction of eligible requests that produce a retrievable, valid file. A diagnostic might be time spent waiting for generation. A guardrail might track requests that include data outside the user's authorized scope, with any occurrence requiring immediate investigation rather than averaging it away.</p>
<h2 id="section-3">Write the denominator in plain language</h2>
<p>Does completion mean completed requests divided by all initiated requests, all valid requests, or all sessions that viewed the page? Each definition answers a different question. State the eligibility rule and keep excluded cases visible.</p>
<p>Define the observation window too. A request that completes tomorrow may look like a failure in today's snapshot. Use mature cohorts when comparing outcomes, and distinguish pending work from completed failures.</p>
<h2 id="section-4">Check instrumentation before interpreting behavior</h2>
<p>Verify event names, duplicate handling, identifiers, and the sequence that connects initiation to completion. An event emitted on button click is not evidence that the server accepted the request. An event emitted before a database transaction commits may overcount success.</p>
<p>Test representative flows, including retries and failures. When instrumentation changes, annotate the break in the series. A measurement change should not be celebrated as a product improvement.</p>
<h2 id="section-5">Choose a review question, not only a target</h2>
<p>A review might ask whether failed exports are concentrated in one file type, whether users return because the first file was unusable, or whether a faster generation path increases support work. That points the team toward a specific investigation.</p>
<p>Targets can focus effort, but a target without a failure analysis can encourage local optimization. Faster average completion may be achieved by rejecting difficult requests. Pair the outcome with coverage and the experience of excluded users.</p>
<h2 id="section-6">Do not infer causality from every movement</h2>
<p>A before-and-after change may reflect seasonality, a different user mix, or an unrelated release. Use an appropriate experiment when causal attribution matters and the conditions support one. Otherwise label the observation honestly and combine it with other evidence.</p>
<p>A useful metrics review ends with a decision, an owner, and a reason. It may conclude that more evidence is needed. See <a href="https://blog.bhaveshjain.com/experiment-small-samples.html">working with limited experimental traffic</a> and <a href="https://blog.bhaveshjain.com/cost-of-average-accuracy.html">reading aggregate model metrics carefully</a>.</p>
<h2 id="section-7">Use a denominator that preserves failures</h2><p>For a synthetic export flow, 100 initiated requests, 80 eligible requests, and 72 valid deliveries yield 90% eligible completion but 72% completion from initiation. Both can be correct measures if named properly; neither explains the 20 ineligible requests. Keep eligibility, pending work, rejection reasons, and valid delivery visible. A single convenient denominator can hide a user-experience failure or an access-policy mismatch.</p><section aria-labelledby="sources-title" class="post-sources"><h2 id="sources-title">Sources and further reading</h2><ul><li><a href="https://www.gov.uk/service-manual/measuring-success/how-to-set-performance-metrics-for-your-service">GOV.UK Service Manual: How to set performance metrics for your service</a></li>
