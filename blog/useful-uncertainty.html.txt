<p>“I don't know” can be a responsible answer and a terrible interface. If it leaves the user with no explanation or next step, the system has merely transferred the problem. A useful uncertainty state helps the user understand what is missing and how to proceed.</p>
<p>The product question is not whether the assistant should always answer or always abstain. It is which conditions justify an answer, which require clarification, and which need a different workflow.</p>
<h2 id="section-1">Name the uncertainty before designing the message</h2>
<p>Missing evidence, conflicting sources, ambiguous intent, and lack of permission are different conditions. They should not all become “something went wrong.” A technical outage is different again: the system may know how to perform the task but be unable to reach a dependency.</p>
<p>In a hypothetical policy assistant, the right response to a missing location might be a clarification question. The right response to contradictory approved policies might be a cited explanation and escalation. A lack of access should not reveal that a confidential document exists.</p>
<h2 id="section-2">Do not turn a feeling into a percentage</h2>
<p>A generated statement of confidence is not automatically a calibrated probability. If a product uses a measured probability to decide when to abstain, validate it on appropriate held-out data and examine whether the relationship holds for important task groups.</p>
<p>Even then, the threshold is a product decision about consequences. An acceptable threshold for suggesting a folder label need not be appropriate for executing an external action. Keep that policy separate from the model's estimate.</p>
<h2 id="section-3">Evaluate what the system declines</h2>
<p>A system can improve the accuracy of its answered cases by refusing more difficult requests. That may be desirable within limits, but the apparent gain does not describe the whole experience. Report both the fraction answered and the quality of those answers.</p>
<p>Also review the declined cases. Which could have been answered safely? Which users or task types are disproportionately routed to manual work? A fallback that always lands on the same small support team may be safe for the model and unsustainable for the service.</p>
<h2 id="section-4">Offer the smallest useful next step</h2>
<p>Ask for a missing field when it could resolve the uncertainty. Offer a relevant source when the user can verify it. Route a case to an accountable reviewer when the decision needs judgment. State that a dependency is unavailable when retrying later is genuinely appropriate.</p>
<p>Do not ask users for information the system will ignore, or promise an escalation that nobody receives. A fallback path deserves the same completion checks as the successful automated path.</p>
<h2 id="section-5">Preserve the boundary in the interface</h2>
<p>A draft, a recommendation, and an executed action should look different. If the system provides a partial answer, identify what remains unresolved rather than blending assumptions into the prose. Keep uncertain content out of downstream automated actions unless the receiving system has an explicit policy for it.</p>
<p>For the policy example, the assistant might summarize the uncontested general rule while saying that the regional exception needs confirmation. Whether that partial answer is useful depends on the task; in some workflows, any unresolved exception should stop the process.</p>
<h2 id="section-6">Make the fallback measurable</h2>
<p>Track whether the user resolves the task after clarification or review, how long that takes, and how often the fallback itself fails. Inspect a sample of confident answers as well as abstentions. Otherwise the team sees the cautious failures and misses the silent ones.</p>
<p>The aim is appropriate reliance: a user who knows when the system can help, when to verify it, and how to continue when it cannot. See <a href="https://blog.bhaveshjain.com/human-in-loop-workflows.html">designing the review queue</a> and <a href="https://blog.bhaveshjain.com/black-box-to-glass-box.html">making evidence inspectable</a>.</p>
<h2 id="section-7">Use disagreement as a signal, not a certificate</h2><p>Research on semantic entropy compares the meaning of repeated model answers rather than only token variation. It can identify some confabulations, but a model that repeats the same systematic mistake can still appear consistent. That is why agreement, confidence language, and answerability need separate checks. Validate an abstention policy on the actual task, including useful answers it unnecessarily declines, and keep an accountable fallback.</p><section aria-labelledby="sources-title" class="post-sources"><h2 id="sources-title">Sources and further reading</h2><ul><li><a href="https://doi.org/10.1145/3290605.3300233">Microsoft: Guidelines for Human-AI Interaction</a></li>
